## 3.0 ✅ 已解决：事件机的「没有结束回合按钮」（v0.2.356）

### 3.0.1 根因（一行）

`src/Hooks/Patches/EmotionChipBossTakeoverPatch.cs` 用 Prefix **跳过**了
`EmotionChip.AfterPlayerTurnStart`，但**没有给 `__result` 赋值**。而那个方法是 **async**：

```csharp
[AsyncStateMachine(typeof(<AfterPlayerTurnStart>d__5))]
public override Task AfterPlayerTurnStart(...) { builder.Start(...); return builder.Task; }
```

Prefix `return false` ⇒ 方法体不执行 ⇒ 返回 `default(Task)` = **null**
⇒ `Hook.AfterPlayerTurnStart` 的状态机里 `model.AfterPlayerTurnStart(...).GetAwaiter()`
直接 **NullReferenceException**（对 null 调扩展/实例方法不会「优雅返回」）。

### 3.0.2 为什么恰好是这个顺序（日志逐行对上）

`Hook.AfterPlayerTurnStart` 分 Early / 正常 / Late 三趟遍历
`combatState.IterateHookListeners()`（全程序集里 `AfterPlayerTurnStartEarly` **没有任何 override**，
所以第一趟不可能出事）。正常那趟里，事件机的遗物按顺序走到：
`选择悖论：对她跳过`（那个 Prefix **有** `ref Task __result`，所以安全）→ **下一个就是情感芯片** → 炸。
日志正好是：
```
玩家回合开始钩子：开始（真人玩家）
选择悖论：对她跳过（…）
玩家回合开始钩子：异常:Object reference not set to an instance of an object.（耗时 2ms）
```
`13:03`（v0.2.354）与 `13:07`（v0.2.355）两场**完全一致** ——
注意 **3.4 节原来说「13:07 那次连选择悖论都没出现」是误读**，两场都有那一行。

### 3.0.3 为什么 v0.2.355 的 finalizer 一点用都没有（**别再试这条**）

`Hook.AfterPlayerTurnStart` 是 async 方法（反编译 `Hook.<AfterPlayerTurnStart>d__56`），
**整个方法体都在状态机里**，异常由状态机自己
`catch (System.Exception e) { builder.SetException(e); return; }` **塞进 Task**，
**永远不会穿过方法边界**。所以：

- `[HarmonyFinalizer]` 挂在返回 Task 的那个壳上 ⇒ `__exception` **永远是 null**（**和 `CombatHasOurBoss` 无关**，
  3.5 节的猜测是错的）；
- 挂在状态机 `MoveNext` 上也**同样没用**（异常不逃出 `MoveNext`）。

**唯一能拦的位置是「拿到 Task 之后」⇒ 必须用 Postfix（`ref Task __result`）。**

### 3.0.6 教训（已写进 `.dshwolf/cerebrum.md` 的 Do-Not-Repeat）

> 凡是用 Prefix **跳过返回 `Task` 的钩子**，必须 `ref Task __result` 并赋 `Task.CompletedTask`。
> 少这一句就是 null Task，下游 `GetAwaiter()` 抛 NRE，**把整条钩子链炸掉**（症状还会伪装成完全无关的 UI 问题：
> 结束回合按钮消失、回合管线不跑、Boss 不出牌）。
> 同理：诊断 async 钩子的异常**只能用 Postfix 检查返回的 Task**，finalizer 永远看不到。

### 3.5 为什么 v0.2.355 的「保险」没起作用 —— ❌ **下面这段归因是错的，已由 3.0.3 取代**

> **真正的答案**：`Hook.AfterPlayerTurnStart` 是 async 方法，异常被状态机 `SetException` 塞进 Task，
> **永不穿出方法边界** ⇒ finalizer 的 `__exception` **永远是 null**，跟 `CombatHasOurBoss` 一点关系都没有。
> 保留原文只为记录「当时怎么想的」，**不要照它去改 `CombatHasOurBoss`**（那处 v0.2.356 顺手加固了，但不是根因）。

我加了两层保险，日志显示**都没生效**：

1. **`Patches/PlayerTurnStartHookSafetyPatch.cs`**（`Hook.AfterPlayerTurnStart` 的 Harmony **finalizer**，
   有我们的 Boss 就吞异常并打 `⚠ 玩家回合开始钩子链抛异常…` + 堆栈）
   ⇒ **没有打出那行**，说明 finalizer 里 `CombatHasOurBoss(combatState)` 返回了 false（于是把异常照原样抛回去）。
   `CombatHasOurBoss` 现在只扫 `combat.Allies` / `combat.Enemies` 两个集合 —— **很可能我们的 Boss 生物不在其中**
   （影子 Player 的生物是挂在敌方侧的，但这两个属性也许按「当前视角」解析）。
   **先把它改成「只要 `combat` 里任何地方能捞到 `CharBossMonster` 就算」**
   （例如 `combat.PlayerCreatures` + `combat.HittableEnemies` + `combat.AllCreatures`，或干脆判断
   `CombatManager.Instance?.History` 之外的东西；退一步：只要 `BuildInfo` 记录「本场有我们的 Boss」的静态标记就吞）。
   **吞掉之后下一次测试：回合开始能走完 ⇒ 按钮应该回来、她应该出牌；同时日志会带出完整堆栈，指名道姓是谁。**
2. **「按钮被藏 2 秒就强制打开」**（`ProbeEndTurnButton` 里 `_endTurnHiddenStreak >= 2` 时反射调
   `SetState(State.Enabled)`）⇒ 也**没有打出** `结束回合按钮保险：…`
   ⇒ 最可能是 `CombatManager.Instance.AllPlayersReadyToEndTurn()` 返回了 **true**（我要求它为 false 才动手）——
   也就是说游戏可能认为「玩家已经点过结束回合」，这本身也是一条线索。

### 3.6 建议的下一步顺序（按性价比）
1. **修 3.5-1 的 `CombatHasOurBoss`**，让 finalizer 真的吞掉异常 ⇒ 先让用户能玩（这是止血）。
2. 拿到堆栈后，**把抛异常的那件东西对我们这只 Boss 单独关掉**（照着 `ChoicesParadoxBossSkipPatch` /
   `EmotionChipBossTakeoverPatch` 的写法，`new HarmonyPatch(typeof(X), nameof(X.AfterPlayerTurnStart))` + 前缀 return false）。
3. 如果 finalizer 还是不触发，说明**异常不在 `Hook.AfterPlayerTurnStart` 里**而是被它包住的下游，
   那就在 `Hook.AfterPlayerTurnStart` 的 prefix 里打一次 `combatState` 里所有监听者清单
   （`IterateHookListeners` 或 `Allies/Enemies` 的每个生物的 `Monster` + 遗物 + 能力），逐个比对。
4. **快速二分法**（最土但最快，且不需要读游戏内部）：
   事件机的遗物栏是 10 件（`Core/EventMachineScript.cs` 的 `Relics()`）：
   `数据磁盘 / 玉之剑 / 涅奥的祝福 / 无礼之茶 / 南瓜蜡烛 / 旺购徽章 / 选择悖论 / 大蘑菇 / 王室猛毒 / 情感芯片`。
   依次删掉一半（先删「王室猛毒 + 情感芯片 + 大蘑菇 + 选择悖论 + 南瓜蜡烛」）再 build+装，
   让用户打一次 `fight DEFECT_EVENT_BOSS_ENCOUNTER`：**能结束回合 ⇒ 元凶就在删掉的那一半里**，再二分。
   这些遗物里 `choicesParadox / royalPoison / emotionChip` 是唯一三个有 `AfterPlayerTurnStart` 的，
   但我已对前两个做了处理，**`royalPoison` 没处理**（它的钩子 `if (player == Owner …)` 对真人玩家应当直接 return，
   不过它内部会读 `Owner.PlayerCombatState.TurnNumber`，如果 `PlayerCombatState` 为 null 就正好是 NRE！**= 强烈怀疑对象**）。
5. 顺带确认：**同样的 NRE 在别的 Boss 战里有没有**（现在只有事件机测过 v0.2.354+ 的构建）。
   让用户随便打一场养手骨/蛇眼猎，看日志里 `玩家回合开始钩子：异常` 有没有出现 ——
   有 ⇒ 是**所有 Boss 战共有的**问题（那更像我们影子玩家的某件通用东西，例如 `NeowBlessing`、`CrackedCore`）；
   没有 ⇒ 就是事件机独有的遗物/卡。
